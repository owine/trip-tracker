# arq Bump: 0.26 → 0.28

> **For agentic workers:** Single-task plan. Dispatch as one implementer (haiku). This is the lowest-risk plan in the deferred-majors batch.

**Goal:** Upgrade `arq` from `>=0.26,<0.27` to `>=0.28,<0.29`. arq is on 0.x where every minor is a "major" by SemVer convention, but the actual change surface is empty.

**Risk level:** TRIVIAL. Confirmed via the upstream HISTORY.rst (research dated 2026-04-30):
- 0.26 → 0.27: dropped advertised Python 3.8 support. **No API changes.**
- 0.27 → 0.28: added Python 3.14 support. **No API changes.**

Every integration point we use survives unchanged:

| Integration | Status |
|---|---|
| `WorkerSettings` class shape | Unchanged |
| `functions = [parse_raw_email]` | Unchanged |
| `max_tries = 5` | Unchanged |
| `keep_result = 0` | **Confirmed** — still named `keep_result` (we recently fixed a `keep_result_seconds` typo; 0.28 keeps the correct name) |
| `RedisSettings.from_dsn(...)` | Unchanged |
| `startup`/`shutdown` async staticmethods on `ctx: dict[str, Any]` | Unchanged |
| `from arq import create_pool` | Unchanged |
| `redis.enqueue_job("parse_raw_email", str(uuid))` | Unchanged |
| `redis.aclose()` | Unchanged |

**Branch:** `chore/arq-bump`. Cut from `main`.

**Soak window:** 3 days (shorter than the standard 7 — risk is low enough that a faster validation is justified, but >24h covers any midweek anomaly).

## Rollback Plan

arq is stateless beyond what's stored in Redis as the task queue. The Redis container has **no volume** in this project (per docker-compose.yml: "No volume — queue is ephemeral, parse_pending recovers backlog."), so any in-flight tasks are lost on container restart regardless. This makes rollback trivial.

**If discovered before tag:**

```bash
git revert <bump-commit-sha>
uv lock
git push origin main
```

**If discovered after tag pushed:**

1. `git revert <bump-commit-sha>` on main, push.
2. The next tag (e.g., v0.3.x) ships with arq pinned back to 0.26.
3. After deploy, run `python -m trip_tracker parse_pending` to re-enqueue any RawEmails that were in flight at the moment of rollback.

**State cleanup:** None at the database layer. The Redis ARQ queue is ephemeral.

## Note on the Anthropic + arq combo

If both bumps land in the same week, **bump anthropic first, then arq**. Reasoning: the anthropic bump touches `parsers/llm.py`, which the worker imports. If anthropic fails, the worker can't even start, and an arq bump at the same moment muddies attribution. Sequential lands keep the rollback target obvious.
